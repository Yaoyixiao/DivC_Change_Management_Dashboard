# 数据导出改造计划（ECR 层级）

## 目标

把取数链路从 RA-OP 4 层结构改造为 ECR 层级结构，配置从硬编码改为读取 `src/ECR_Config.xlsx`：

- **ECR**（根，10 个 ID 来自配置表 'ECR' sheet）
  - **Work Item**：经 ECR 的 `ALM_Work Items` 字段递归导出，最多 3 级（L0/L1/L2，hop 数 0/1/2，L2 不再下钻）
  - **Action**：经 ECR 的 `ALM_Actions` 字段导出（仅从 ECR 收集）
  - **Build**：经 ECR 的 `ALM_Work Item For` 字段导出（仅从 ECR 收集）
- 所有 item 统一使用 'Data_Field' sheet 的 42 个字段导出
- 输出四件套全保留，文件名不变：`data.xlsx`、`dashboard.db`、`dashboard_manifest.json`、`dashboard_schema.json`

## 数据模型（按你选择的"通用节点表"）

**SQLite**（`database_writer.py` 动态生成，列名由字段表推导）：

```sql
CREATE TABLE metadata (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- metadata: schema_version / generated_at / config_file / root_item_ids(JSON)

CREATE TABLE items (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,      -- 'ecr' / 'work_item' / 'action' / 'build'
  level INTEGER,           -- 仅 work_item 有值: 0/1/2 (距 ECR 的 hop 数)，其余 NULL
  <42 个字段列>            -- "ALM_Planned Start Date" → planned_start_date，全部 TEXT；*_date 列写 ISO 文本
);

CREATE TABLE edges (
  parent_id INTEGER NOT NULL,
  child_id INTEGER NOT NULL,
  relation TEXT NOT NULL,  -- 'work_items' / 'actions' / 'work_item_for'
  PRIMARY KEY (parent_id, child_id, relation)
);
-- 索引: items(kind), edges(child_id), edges(relation)
```

**Excel**（3 个 sheet，沿用现有表头样式/冻结/筛选）：`Items`（ID, Kind, Level + 42 字段列）、`Edges`（Parent ID, Child ID, Relation）、`Metadata`（导出时间 + 各 kind/关系计数）。

**manifest / schema JSON**：表结构、计数全部由字段表与实际数据动态生成，不再硬编码。

## 验证方式

1. `python src/selftest_fetch.py`：无 PTC 环境下的全链路回归（本机即可跑）。
2. `node --check` 不适用（无前端改动）；Python 侧用 selftest + `sqlite3` 读回断言。
3. 真实取数需在装了 PTC 客户端（`im` 在 PATH）的内网机器执行 `python src/fetcher.py`——字段表 42 个字段对 4 类 item 是否全部有效只能在真实环境确认；若 PTC 对某些 item 类型拒绝某字段，cli_client 现有的 RuntimeError 会带出 stdout/stderr，届时再按类型过滤字段（预留扩展点，不在本次范围）。

## 语义约定（写进代码注释与 README）

- level = 距任一 ECR 沿 `work_items` 边的最小 hop 数（0/1/2），首次发现即定，不随更短路径更新（BFS 保证首现即最短）。
- 边只记录遍历方向上的边（父 → 本 hop 新发现子），不记录回指/跨层边，杜绝环。
- 根 ID 在 PTC 不存在时静默少于配置数量，log warning 不报错。
- CLI 输出仅用 ASCII（Windows cp1252 约束，沿用原约定）。
